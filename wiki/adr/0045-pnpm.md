# ADR-0045: pnpm for the frontend and the docs site

## Status

Accepted. `aqua:pnpm/pnpm` is in `mise.toml` and `mise.lock`; both projects name it in `packageManager`, configure it in their own `pnpm-workspace.yaml` and lock with `pnpm-lock.yaml`.

## Date

2026-11-25

## Context

The frontend and the docs site were npm projects: the npm that the pinned Node bundles, `package-lock.json`, every install `npm ci --ignore-scripts`, and an `allowScripts` field as the install-script policy. The docs site held its lockfile to a seven-day release age (`min-release-age=7`); the frontend had none, so its lock held releases published days earlier. The [tooling assessment](../tooling-assessment.md#2-the-frontends-and-the-docs-sites-packages-pnpm-and-pnpm-lockyaml) compared npm, pnpm, Yarn and Bun and left the choice to the maintainers.

What weighed: whether a release-age floor holds for transitive dependencies and is checked again at install, whether an unreviewed install script fails the install rather than being skipped quietly, whether a drop in a package's trust evidence (trusted publishing, provenance) is caught, and whether the tool itself installs checksum-verified like the rest of the toolchain ([ADR-0043](./0043-mise-for-the-developer-toolchain.md)).

## Decision

pnpm is the package manager of `frontend/` and `docs-site/`, each a project of its own (its own `pnpm-workspace.yaml`, no shared workspace: they share no code).

- **The tool.** The standalone release, `aqua:pnpm/pnpm` in `mise.toml`, locked in `mise.lock` with a sha256 per platform and its GitHub artifact attestation, linked as `.tools/bin/pnpm`. `packageManager: "pnpm@<version>"` in both `package.json` files; no corepack (Node 25 and later do not bundle it). `pmOnFail: error` makes a different pnpm fail instead of downloading the named one unverified, and `scripts/check-pnpm-version.mjs` runs first in CI and in the image build. The image takes the same release, checked by BuildKit against `PNPM_SHA256_AMD64` (mise.lock's linux-x64 sha256, a test keeps the two equal) or `PNPM_SHA256_ARM64` (the release's asset digest, which `make pins-refresh` checks and writes; mise.lock holds no linux-arm64, and adding that platform would re-lock every tool for one consumer).
- **The settings** (pnpm's [dependency resolution](https://pnpm.io/settings/dependency-resolution) and [build](https://pnpm.io/settings/build) settings): `minimumReleaseAge: 10080` (seven days, transitive included, and checked against every lockfile entry on a frozen install); `strictDepBuilds: true` with `allowBuilds` taken from the old `allowScripts` (every package with a script denied); `blockExoticSubdeps: true`; `trustPolicy: no-downgrade`; the store and cache under `.tools/pnpm/`.
- **Every install** is `pnpm install --frozen-lockfile`: CI, the kind job, the image build and the documented local install. No `--ignore-scripts`: it would also switch the unreviewed-script check off, while `allowBuilds` already runs none.
- **The locks** came from `pnpm import` of the old `package-lock.json` files. The docs site's resolved set is identical (576 `name@version` pairs). The frontend's differs only in three listed ways: 53 versions younger than seven days moved to the newest release at least seven days old (no known vulnerability returned, checked with the pinned OSV-Scanner); pnpm's one version per parent (`brace-expansion` 1.1.21 and 1.1.22 under `minimatch@3.1.5` became 1.1.22, which satisfies the declared `^1.1.7`); and `semver` 6.3.1 → 6.3.2, because the trust policy rejects 6.3.1.

## Consequences

- Good: the frontend's lock is held to the same seven days as every other pin, and a lock that bypasses the floor fails the install, not just the next resolution.
- Good: a new install script fails the install (`ERR_PNPM_IGNORED_BUILDS`) instead of being skipped quietly; a trust downgrade fails it too.
- Good: pnpm installs checksum-verified and attested from `mise.lock`, the same path as every other tool, and the image's copy is held to the same sha256.
- Bad: every adopter learns a second package manager's commands (`pnpm install --frozen-lockfile`, `pnpm run`, `pnpm exec`), and an exception (a young security fix, a trust downgrade) is an entry in `pnpm-workspace.yaml` with its reason; a test fails once a release-age exception has outlived its seven days.
- Bad: a Renovate bump of pnpm touches `mise.toml`, both `packageManager` fields, both lockfiles' pnpm record and the image's checksums; `make pins-refresh` writes the image's, and the pull request's note says the rest.
- Bad: pnpm keeps a small state file for its update check that a project cannot move; the Makefile and the git hooks set `XDG_STATE_HOME` into `.tools/`, a bare `pnpm` call writes it under `~/.local/state`.

## Alternatives considered

- **npm with the floor settings** (`min-release-age=7`, `allow-git=none`, `allow-remote=none` in an `.npmrc` per project, `allowScripts`): no install changes, but no trust-downgrade check, `npm ci` does not apply the release age to the lock, and a new install script is skipped quietly until npm 12, which no Node LTS bundles yet.
- **pnpm, chosen:** the release age checked against the lock, strict build failures, the trust policy, and a standalone release mise verifies.
- **Yarn (Berry):** scripts off by default and an age gate, but a new lockfile format and Plug'n'Play or a linker setting to manage, with no trust-downgrade check.
- **Bun:** a release-age setting (off by default) and `trustedDependencies`, but a different runtime as well as a package manager.

### Upgrading

The adopter actions: the steps an existing release needs, gathered from the entries below (each links the section that
holds it). [Template upgrades](./template-upgrades.md) says how to bring a release in.

- **Re-run `scripts/k8s-bootstrap.sh <env>` before the next deploy.** The deployer Role in the database namespace gains `configmaps` (the restore check's ConfigMap; [Disaster Recovery](./disaster-recovery.md); [the bootstrap](./infrastructure.md#namespace-bootstrap-one-time-admin-step)). With `monitoring.flavour: gmp`, the same re-run applies the new cluster alerts' `ClusterRules`, which the deploy never renders ([Alerts](./operations-runbook.md#alerts)).
- **Set `monitoring.runbookUrl` to your repository's runbook before production** (then re-run the bootstrap for gmp): the production render refuses the placeholder ([Alerts](./operations-runbook.md#alerts)).
- **Expect two new `critical` SLO alerts on upgrade** wherever the rules render; tune `monitoring.slo`, or opt out with `monitoring.slo.enabled: false` ([Service Level Objectives](./operations-runbook.md#service-level-objectives)).
- **Queries over the labelled latency histogram see new `le` series** ([Prometheus Metrics](./operations-runbook.md#prometheus-metrics)).
- **`HighErrorRate` no longer counts the probe and scrape handlers** ([HighErrorRate](./operations-runbook.md#higherrorrate)).
- **Raise `postgresql.backup.deadlineSeconds` (3600) first if the nightly dump takes longer than an hour.** The deadline now ends the backup Job and it fails (`BackupJobFailed`, then `BackupTooOld`) ([Database Backup CronJob](./database.md#database-backup-cronjob)).
- **Pass the same values to `scripts/migrate-to-bootstrap.sh` as the deploy, and the admin's bootstrap values as `--bootstrap-values`.** Without the admin's own `--bootstrap-values` the bootstrap can apply other RBAC than the admin's; on a release already migrated, re-apply `scripts/k8s-bootstrap.sh <env> --values FILE | kubectl apply -f -` ([Infrastructure](./infrastructure.md#namespace-bootstrap-one-time-admin-step)).
- **Re-run `scripts/github-settings.sh --apply`** for the squash-only merge settings that `pr-title.yml` relies on ([GitHub repository settings](./github-repository-settings.md#what-the-script-sets)).
- **release-please runs on the push that merges this change wherever `RELEASE_APP_ID` is set**, which is every repository whose settings were applied (`--apply` requires it). Before merging: add Issues: read and write to the release App and accept the permission change on its installation; if the repository has history, commit `bootstrap-sha` in the same merge; and re-run `scripts/github-settings.sh --apply` from the updated checkout, so the Actions allowlist has the two new actions. A repository without the variable gets a notice only, until the App is set up ([The release GitHub App](./github-repository-settings.md#the-release-github-app)).
- **Re-run `scripts/github-settings.sh --apply`: the `main` ruleset loses its admin bypass.** From then on nobody, the admin included, merges a pull request until `CI OK` is green; in an emergency an admin turns the ruleset off in **Settings → Rules** and back on after ([GitHub repository settings](./github-repository-settings.md#what-the-script-sets)). The upstream template repository also passes `--template`. Replace the owners in `.github/CODEOWNERS` and the contact in `CODE_OF_CONDUCT.md` (or set `CODEOWNER` and `DOMAIN` and run `infra/adapt/adopt.sh`).
- **Re-run `scripts/github-settings.sh --apply` to publish the documentation site**: it turns GitHub Pages on with Source: GitHub Actions and manages the `github-pages` environment (branch `main` only); until then `docs-site.yml` is a green no-op ([GitHub repository settings](./github-repository-settings.md#what-the-script-sets)). **If your repository already publishes Pages from a branch** (a `gh-pages` Helm index, say), the script leaves it as it is, reports a skip and exits 3; switching the source to GitHub Actions stops that branch publishing, so do it by hand only if the docs site should replace it.
- **Optional: turn on the AI reviewer.** An Anthropic API key with a spend limit, the `ai-review` environment with that key as `ANTHROPIC_KEY`, then `PR_AGENT_ENABLED=true` ([AI pull request review](./ci-cd.md#ai-pull-request-review)). Unset, nothing runs.

### Security
- **MIT Kerberos CVE-2026-112314, CVE-2026-112320, CVE-2026-112321, CVE-2026-112322, CVE-2026-112323 and CVE-2026-119079 (High) are fixed in the backend image, before its distroless base ships the fix.** The base's `libkrb5-3`, `libgssapi-krb5-2`, `libk5crypto3` and `libkrb5support0` are `1.21.3-5+deb13u1`, and the blocking Grype gate failed on them. The backend's `DEBIAN_FIXES` now lists them at Debian's `1.21.3-5+deb13u2`; the newest distroless Debian 13 base still ships `u1`, so a digest bump cannot clear it. **Nothing to do when adopting.** See [Containerization](./containerization.md#debian-fixes-the-base-has-not-shipped-yet).
- **glibc CVE-2026-19499 and CVE-2026-5435 (High) are fixed in all three images, before their distroless bases ship the fix.** Debian fixed them, with twelve Medium and Low glibc CVEs, in `2.41-12+deb13u5`, but no distroless Debian 13 base had been rebuilt with it, so the blocking Grype gate failed on every image. Each Dockerfile now has a `debian-fixes` stage: `DEBIAN_FIXES` lists `<package>=<version>` fixes, `scripts/docker/debian-fixes.sh` downloads them from the Debian archive (checked against its signed indices) and unpacks them with their dpkg records, and the runtime stage copies them over the base, so the image and its SBOM carry the fixed glibc. The build refuses an entry the base already has, so a fix is removed when Renovate moves the base digest past it and never downgrades the base. **Nothing to do when adopting**; when a Renovate base-digest pull request fails with "the base already ships", delete the entry it names. See [Containerization](./containerization.md#debian-fixes-the-base-has-not-shipped-yet).

### Changed
- **A curated documentation site.** [`docs-site/`](../docs-site/README.md) (Astro + Starlight, [ADR-0041](./adr/0041-documentation-site.md)) puts a reading path in front of the wiki; the contributing guide and the Cloudflare and GKE walkthroughs are loaded from their files, never copied. Every pull request that touches its inputs builds it strictly (a broken link or `#anchor`, invalid front matter or a failing diagram fails it) and scans it with axe; [`docs-site.yml`](../.github/workflows/docs-site.yml) publishes it to GitHub Pages from `main`, and is a green no-op until Pages is enabled ([CI/CD](./ci-cd.md#documentation-site)).
- **CI survives two transient network failures.** The Playwright install is split into a system-deps step and a browser-download step, each with its own timeout and one bounded retry (`scripts/ci/retry.sh`), so a stalled install no longer uses up the job's budget; the release `merge` job retries `docker buildx imagetools create` up to three times when ghcr.io times out. **Nothing to do when adopting.** See [CI/CD](./ci-cd.md).
- **A pull request with the `breaking-change` label needs a breaking title.** `pr-title.yml` refuses a labelled pull request whose title lacks the Conventional Commit `!` (`type(scope)!: subject`), so a breaking API change always moves the major version; the check now also runs on `labeled` and `unlabeled`. **Nothing to do when adopting.** See [API lifecycle](./api-lifecycle.md).
- **CSP reports pass the WAF.** With the WAF and `cspReporting.enabled` on, CRS answered every browser report with a 403 (its content types are not in CRS's list, and the body, which quotes the policy and URLs, scores as XSS and SSRF). A `POST` of one of the two report types to the report route alone now gets them as its allowed types and its body uninspected (its URI, query and headers still inspected); the backend caps and sanitises it ([CSP Violation Reports](./security.md#csp-violation-reports)).
- **The WAF no longer turns a backend Pod's shutdown into a 503.** It affected releases with the CRS on (`waf.owaspCrs`, the default). A backend Pod that gets SIGTERM closes its idle keep-alive connections, and Envoy could have just written a request to one (`503`, flag `UC`). `GET`, `HEAD` and `OPTIONS` are now resent on such a reset; every other method goes to a second upstream cluster with one request per connection, so it never lands on a pooled connection a Pod is closing, and is resent only when nothing was sent yet. **Nothing to do**; at very high write rates, see the TIME_WAIT note in [Security, Runtime Application Protection](./security.md#runtime-application-protection-dast--waf).
- **`HighErrorRate` leaves out the probe and scrape handlers.** It now counts the same requests as the SLOs and the RED dashboard (`handler!~` `monitoring.slo.excludeHandlers`), so 5xx answers on the health probes or `/metrics` alone no longer fire it. **Nothing to do.** See [HighErrorRate](./operations-runbook.md#higherrorrate).
- **The backend's labelled latency histogram has new buckets.** `http_request_duration_seconds{method,handler}` now has the bounds 0.05, 0.1, 0.25, 0.5, 1, 2.5 and 5 s (was 0.1, 0.5, 1), so the latency SLO can pick a threshold. Dashboards and queries over `http_request_duration_seconds_bucket` see new `le` series; the old bounds keep their names. See [Prometheus Metrics](./operations-runbook.md#prometheus-metrics).
- **Compatibility: the chart needs Kubernetes 1.34 or later (was 1.30), and the floor is now a tested floor.** Kubernetes 1.30 has been end-of-life upstream since mid-2025. `kubeVersion` is now `>=1.34.0-0`, the oldest minor the kind job installs and tests the chart on; at 1.34 every feature the chart relies on is GA (the preStop `sleep` action, GA in 1.34; native sidecars, GA in 1.33). The Pod Security version labels of the namespaces (the bootstrap's `podSecurityVersion` and the chart's own Namespace templates) move to `v1.34`, and kubeconform validates against the Kubernetes 1.34 OpenAPI spec (`tools/pins.tsv`, `k8s-openapi` 1.34.13). **A cluster older than 1.34 refuses the install: upgrade the cluster first.** Re-apply the bootstrap (`scripts/k8s-bootstrap.sh <env> | kubectl apply -f -`) to move the namespace labels.
- **Production rules, and placeholders the deploy refuses.** With `environment: production` the chart refuses to render unless every image it renders has a digest, the database is managed (`postgresql.enabled` false, with `externalDatabase` or `cloudSqlProxy`), `config.AUTH_MODE` is not `none` (unless `config.ALLOW_ANONYMOUS` is `"true"`, as the backend requires), the backend and frontend run at least 2 Pods (the HPA minimum while it is on) and both PodDisruptionBudgets keep a Pod. An image digest must be `sha256:<64 lower-case hex>` (or empty) in every environment. `values.production.yaml` now holds the placeholder digest (`sha256:` and 64 zeros) for the app images and `AUTH_MODE: oidc` with a placeholder `OIDC_ISSUER` and `OIDC_AUDIENCE`; `guards.rejectPlaceholders`, which the deploy sets, now collects every placeholder it finds (hosts, Gateway, digests, OIDC, the Cloud SQL instance, the secret store) and fails once, naming each field. `AUTH_MODE`, `ENV` and the proxy's `DB_SSLMODE` check are read as the backend reads them (trimmed, case-insensitive), and an `AUTH_MODE` the backend does not know is refused. In production each `backend.extraInitContainers` image must carry a digest. **Before the first production deploy, set your OIDC issuer and audience (or another auth mode) in `values.production.yaml`**; the deploy sets the digests. `deploy-env.sh`'s first render, which finds the images that run, no longer sets the guard and finds an image by tag or by digest. The WAF Pod rendered `imagePullSecrets` twice when `global.imagePullSecrets` was set; it renders it once. See [Infrastructure, Production rules](./infrastructure.md#kubernetes-resources).
- **kubeconform validates every render, offline.** `make kubeconform` (and the chart job in CI) validates each environment, edge mode and monitoring flavour, every optional object, the Cloud SQL proxy and the admin bootstrap with `kubeconform -strict`, against local schemas only: the Kubernetes kinds from the pinned OpenAPI spec of the chart's `kubeVersion` floor (`tools/pins.tsv`, `k8s-openapi`), the CRDs (Gateway API, the GKE Gateway policies, Google Managed Prometheus, External Secrets, the Prometheus Operator) from `charts/your-service-name/ci/crds`, generated from pinned upstream CRDs (`make crd-schemas`; `make crd-schemas-check` in CI). See [Validating every render](./infrastructure.md#validating-every-render-kubeconform).
- **Metrics moved to their own port, and scrapers must target it.** The backend served `/metrics` on the API port; it now serves it on `config.METRICS_PORT` (`9102`) from the launcher, and the API app has no `/metrics` route (a request to it is a 404). The Service gains a `metrics` port, the ServiceMonitor scrapes it, the `prometheus.io/port` annotation names it, and the scrape NetworkPolicy admits the collector to that port only, so the monitoring namespace no longer reaches the API port. Metric names and labels are unchanged. **Point any scrape you wrote yourself at the Service's `metrics` port (or the Pod's `METRICS_PORT`), and pick a value that clashes with no other container port in the Pod.** The probe and rate-limit exempt lists no longer hold `/metrics`. `networkPolicy.monitoringExtraPeers` (empty by default) admits extra peers, such as a node range, to the metrics port only.
- **One launcher for every way of starting the backend.** `run_backend.sh` (kept, so the documented `./run_backend.sh` still works: it bootstraps the venv, loads `.env`, migrates, then execs the serve module), `infra/runtime/entrypoint.sh` and the CI job that boots the backend now run `python -m your_service_name.backend.serve` like the image, instead of bare `uvicorn`. The metrics server, the graceful timeout and the fixed Uvicorn options are identical everywhere, and a test fails if any launch path runs bare `uvicorn`. **Hot reload stays**, as the serve module's own `BACKEND_RELOAD=true` option (on by default in `run_backend.sh`, off in the entrypoint and the image): Uvicorn then runs an app factory in each reload child, which starts the metrics server and returns the app. The launcher refuses `BACKEND_RELOAD` when `ENV` is production.
- **GMP alerts: app rules in `Rules`, cluster rules in `ClusterRules`.** A namespaced `Rules` object evaluates only series of its own namespace, so with `monitoring.flavour: gmp` it holds the backend's own alert (`HighErrorRate`, group `app-health`) and the kube-state-metrics and cAdvisor alerts are a cluster-scoped `ClusterRules` (`monitoring.googleapis.com/v1`). The deployer has no cluster rights, so the deploy never renders it (`monitoring.gmp.clusterRules.enabled: false`): **set `gmpClusterRules: true` in the bootstrap values and re-run `scripts/k8s-bootstrap.sh`**, which renders it from the chart (like the app's Role). `monitoring.gmp.objectNamespaceLabel` (default `exported_namespace`) names the label that holds the object's namespace on kube-state-metrics series: a third-party report says GMP relabels it so; verify it against your GMP. The deployer Role gains `podmonitorings` and `rules` (`monitoring.googleapis.com`), which the gmp flavour renders. The prometheus-operator flavour is unchanged except that `HighErrorRate` is now in its own group, `app-health`, and `BackupJobFailed` also selects the database namespace (`namespace="<db namespace>"`), as the gmp rule does. The bootstrap refuses `gmpClusterRules: true` for an environment whose chart flavour is not `gmp` (`--chart-values FILE` layers extra chart values for that read). The launcher reads `ENV` for the reload refusal like the app does, `.env` included. A render fails when `config.METRICS_PORT` is the API port or the Cloud SQL proxy's health port.
- **`monitoring.flavour: prometheus-operator | gmp`.** `gmp` renders a `PodMonitoring` and a `Rules` object (`monitoring.googleapis.com/v1`) instead of the ServiceMonitor and the PrometheusRule, from the same rule groups. The flavour also sets the default scrape peers: the `monitoring` namespace and `app.kubernetes.io/name: prometheus`, or `gmp-system` and `app.kubernetes.io/name: collector` (`gke-gmp-system` on Autopilot: set the selectors); explicit selectors still replace them. See [Metrics port and monitoring flavours](infrastructure.md#metrics-port-and-monitoring-flavours), including the case of a collector that arrives from a node address.
- **The WAF is an image this repository builds, and it fetches nothing at runtime.** New `Dockerfile.waf`: the distroless Envoy image (`distroless-v1.39.6`, the newest supported minor; Coraza's own CI stops at the end-of-life 1.33, so the pin was proven by a run: the Wasm loads, benign requests pass, XSS and a SQLi body get 403) by its index digest, plus the Coraza proxy-wasm `0.6.0` release asset, pinned by version and sha256 (`ADD --checksum`, trust on first use; Renovate proposes new versions). `.github/container-images.yml` lists it as `waf`, so pull requests build and check it, and the release builds, scans, signs and attests it like the two app images; `infra/security/config.yaml` scans it; the deploy passes its digest (`DEPLOY_IMAGES` adds `waf`; `deploy-env.sh` renders the release first; an image a rendered container runs, by reference or by component label, needs its digest (fail closed), and only one the release does not run may lack it). The chart runs `images.waf` and loads the Wasm from the image's file (`code.local.filename`, the `envoy.filters.http.wasm` filter): **`waf.envoyImage` and `waf.wasmImage` are removed and refused; set `images.waf` (registry and repository) in your values.** The Pod runs as the image's user (65532, was 101) with a read-only root filesystem and an in-memory `/tmp`. **Coraza now inspects request bodies:** its recommended configuration (`@recommended-conf`), `SecRuleEngine On`, `SecRequestBodyAccess On`, `SecResponseBodyAccess Off`, with `SecRequestBodyLimit`, `SecRequestBodyInMemoryLimit`, `SecRequestBodyLimitAction Reject` and Envoy's listener buffer (`per_connection_buffer_limit_bytes`) all set from the new `config.MAX_REQUEST_BODY_BYTES` (10 MiB), which also sets the backend's limit through the ConfigMap (the backend's built-in default is kept equal by a test), then CRS as before. A 2 MiB body passes; a larger one than the limit is a `413`. An Envoy buffer filter between Coraza and the router holds each request until Coraza has passed all of it, so a request whose body never finishes is never forwarded. Envoy's overload manager bounds its heap at 80% of the WAF memory (`shrink_heap` at 0.90, `stop_accepting_requests` at 0.95). New `waf.extraDirectives` (empty) appends Coraza rule exclusions after CRS; the docs show how to allow binary uploads for a POST to one exact path. The WAF normalises paths (`normalize_path`, `merge_slashes`), refuses encoded slashes (`400`) and cuts off slow clients (`408`): new `waf.timeouts.requestHeadersSeconds` (10) and `waf.timeouts.requestSeconds` (120, at least `edge.gateway.gke.timeoutSec` when that policy is on). The WAF's health port must differ from its traffic port (the render fails otherwise). `healthcheck_exempt` is allowed only for the `waf` image, and an exempt image must declare no HEALTHCHECK. Renovate versions Envoy's `distroless-vX.Y.Z` tag, so new Envoy releases are proposed. Envoy's admin interface is disabled; a health listener (`waf.health.port` 8090, `waf.health.path` `/healthz`) answers a fixed `200`, the startup, readiness and liveness probes ask it, and the NetworkPolicy admits no Pod to it. `image-checks` gains a per-image `healthcheck_exempt: <reason>` (the WAF image has no binary to probe with). See [Containerization, Dockerfile.waf](./containerization.md#dockerfilewaf).
- **Breaking values and deploy changes, with the migration step for each:**
  - `waf.envoyImage` and `waf.wasmImage` are removed and refused. **Delete them, and set `images.waf` (`registry`, `repository`, `tag`) like `images.backend`**; the release supplies its digest.
  - The WAF runs as uid and gid 65532 (was 101). **Nothing to do** unless a policy of yours (an OpenShift SCC, a Kyverno rule) names 101: allow 65532.
  - `postgresql.image` and `postgresql.clientImage` are now `{repository, tag, digest}`; a string is refused. **Rewrite `image: postgres:16-alpine` as `image: {repository: postgres, tag: 16-alpine, digest: "sha256:..."}`**, or delete your override to take the chart's pin.
  - The WAF inspects request bodies. **Before enabling it in production, watch the WAF log in QA**: a legitimate body that CRS flags is now a 403. A body larger than `config.MAX_REQUEST_BODY_BYTES` is refused by the WAF as by the backend; raise the one value if you need more.
  - `DEPLOY_IMAGES` now includes `waf`. **Nothing to do for a new release** (it builds the WAF image). Redeploying an older release, whose digest file has no `WAF_IMAGE_DIGEST`, works while the WAF is off and fails only when `waf.enabled` is true: release again first.
- **The WAF's upstream is configurable.** `waf.upstream.host` and `waf.upstream.port` (empty: the backend Service and port) let an auth proxy sit behind the WAF; `waf.upstreamPeers` (NetworkPolicy peers) replaces the backend Pods in the WAF's egress, on the upstream port. A host without peers fails the render. See [Security, the identity trust boundary](./security.md#the-identity-trust-boundary).
- **Every third-party image in the chart is pinned by digest.** `postgresql.image` and `postgresql.clientImage` become `{repository, tag, digest}` (**a string value is now refused**; `postgres:16-alpine` by its index digest) and `cloudSqlProxy.image` gets the `2.28.0` index digest. A test walks every values file and fails on a third-party image without a digest; Renovate's split-format manager refreshes each.
- **Rolling updates, resources and graceful shutdown.** The backend and frontend Deployments roll with `maxUnavailable: 0`, `rollout.maxSurge` (`25%`), `minReadySeconds` (`10`) and `progressDeadlineSeconds` (`600`). Every container (backend, frontend, WAF, Cloud SQL proxy, the migration Job's two, PostgreSQL, the backup jobs) has a CPU request and a memory limit equal to its memory request, in the standard `{requests, limits}` shape: `limits.memory` is rendered from the request when unset, a different value fails the render, **no CPU limit is set unless `limits.cpu` is**, and other limits (`ephemeral-storage`, `hugepages-*`) pass through. **CPU limits are off by default**, so a values file that set `limits.cpu` (the old defaults did, such as `1` for the backend) now needs it set again to keep it; a memory limit above the request now fails the render, so set `requests.memory` to the memory you want. New `resources.waitForDb`, `migration`, `postgresql` and `pgBackup` blocks hold what was hard-coded. Memory requests and limits: backend and frontend 1Gi (the former limit; the in-memory `/tmp` counts against it, so tune it down with load data), WAF 512Mi, PostgreSQL 1Gi, migrate and backups 512Mi, proxy and `wait-for-db` 128Mi. Requests rose from 256Mi, so the bootstrap quota is now `requests.memory` and `limits.memory` 27Gi and 30 pods (sized from the chart's worst case by a test; re-apply the bootstrap) and the HPA's `targetMemory` (a share of the request) now triggers at a higher absolute use: lower it if you relied on the old point. `preStop` is the native `sleep` action (the exec hooks needed an interpreter in the image), and `terminationGracePeriodSeconds` is derived: `shutdown.preStopSeconds` + the drain (`config.BACKEND_GRACEFUL_TIMEOUT`, or `shutdown.frontendDrainSeconds`) + `shutdown.marginSeconds` (45 s backend, was 60; 30 s frontend). **The chart needs Kubernetes 1.34 or later** (`kubeVersion`; see the tested-floor entry above). The WAF container gets its `waf.resources`, which were never rendered. See [Infrastructure, Workloads](./infrastructure.md#workloads-rollout-resources-and-shutdown).
- **`externalDatabase.port` is removed.** `config.DB_PORT` is the one database port: the stub Secret, the egress rules, the ConfigMap, the Cloud SQL proxy and the in-cluster server all read it. The schema refuses `externalDatabase.port`; **delete it from your values and set `config.DB_PORT` if the port is not 5432.**
- **The namespace quota is computed, and memory limits compare as quantities.** `tests/backend/test_chart_quota.py` renders each environment with every option on and computes the worst case (each Deployment at its HPA maximum plus the rollout surge plus a wave of terminating Pods, the WAF, sidecars and the migration Job, counted as Kubernetes counts init and sidecar containers); the bootstrap quota must be at least 1.2 times that, so a bump of replicas, an HPA maximum or a request fails until the quota rises with it. The quota is now 27Gi memory (requests and limits), 30 pods, 6 CPU. In `resources`, `limits.memory` and `requests.memory` compare as quantities (`1Gi` equals `1024Mi` and `536870912`).
- **One source for ports and probe paths.** The backend and frontend container ports and the frontend `PORT` follow `config.BACKEND_PORT` and `config.FRONTEND_PORT`; the database port (`config.DB_PORT`) now drives the PostgreSQL server (`-c port=`), its Service, probes and policies, the backend and migration egress rules and the backup jobs (`PGPORT`); NOTES prints the configured port. The Deployments take their probe paths from the chart's helpers. A test renders the chart with every port moved and fails on a default literal.
- **The migration Job takes no env from the app ConfigMap.** `envFrom` and `configMapKeyRef` are gone from both containers: it gets an explicit list from the same values and helpers (`ENV`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_SSLMODE` and the two timeouts when `config` sets them, `DB_SSLROOTCERT`), with `DB_USER` and `DB_PASSWORD` from the app Secret only (no longer the whole Secret). The other app settings no longer reach the Job, so its runner keeps just the production database checks: with `ENV=production` it refuses SQLite, a missing URL and an unverified TLS mode to a remote host before connecting (`Settings.for_migration`; the app's startup checks are unchanged, `Settings._database_problems` is now `database_problems`). The Job stays a plain release resource, not a Helm hook (Helm waits for readiness before post-install hooks, and readiness needs the schema: a deadlock); see [Database](./database.md#the-migration-job).
- **Exactly one secret source; a values password together with `secrets.existingSecret` now fails the render** (it was ignored silently), as does any second source. With the in-cluster PostgreSQL and `existingSecret` or the ExternalSecret, set the new `postgresql.existingSecret`: the render fails without it, and the chart no longer renders an empty database password in any mode.
- **`externalDatabase.egressCIDR` is not required when `cloudSqlProxy.enabled`** (the app dials loopback).
- **The chart no longer creates its namespaces or quota; a one-time admin bootstrap does.** `namespaces.create` (new) defaults to `false`: the chart assumes both namespaces exist, and `true` renders its two Namespace objects as before (now with `helm.sh/resource-policy: keep`). The ResourceQuota and LimitRange left the chart (`quota.*` and `limitRange.*` are gone from `values.yaml` and the schema, so a values file that still sets them fails to render). `scripts/k8s-bootstrap.sh <dev|qa|production|local>` renders `infra/k8s/bootstrap/` to stdout, never contacting a cluster: the app namespace and, with the in-cluster database, the database namespace, the quota and LimitRange (the chart's former values, without CPU limits), in each namespace a `bootstrap-deployer` Role and RoleBinding, and the app's own Role and RoleBinding rendered from the chart's `templates/rbac.yaml` (the chart renders them only with the new `rbac.create`, default `false`). The deployer gets Helm's verbs on exactly the kinds the chart renders there, plus Helm's release Secrets, and read and port-forward for the deploy's checks; never `pods/exec`, a wildcard, `escalate`, `bind`, `impersonate`, namespaces, quotas or any Role or RoleBinding. A test derives that kind list from the chart. **The database namespace is now `restricted`** (it was `baseline` enforced), like the app namespace; a new test checks every Pod template in every mode against the restricted profile's rules. The optional WAF Deployment gained the securityContext it lacked (uid 101, RuntimeDefault seccomp, no privilege escalation, no capabilities), without which the restricted app namespace refused it. `deploy-verify.sh` now asks each Pod's health route over a port-forward with the runner's `curl` (same routes, 5 s timeout, a 3xx is unhealthy) instead of running a probe inside the Pod. The deploy and `scripts/k8s-env.sh` pass `--history-max 5` to `helm upgrade` and `helm rollback`, and the bootstrap's Secrets quota (15) covers that history, the chart's Secrets and headroom. - **The backups deploy and run on any storage class.** The backup PVC (`postgresql.backup.enabled`, on by default with the in-cluster database) had no consumer until the first nightly backup, so on a `WaitForFirstConsumer` class (kind, GKE's `standard-rwo`, EKS's gp2 and gp3), or on a cluster with no class named `standard`, it stayed `Pending` and every deploy's `helm --wait` timed out and rolled back. The PostgreSQL Pod now mounts it read-only (one PostgreSQL restart on upgrade), the backup and verify CronJobs carry a required `podAffinity` to that Pod (the volume is ReadWriteOnce), and `className: ""` (`postgresql.storage` and `postgresql.backup.storage`) uses the cluster's default class. The database's NetworkPolicy also never admitted the backup jobs (and their Pods carried no labels to admit), so no backup could connect where NetworkPolicy is enforced: their Pods now carry the chart's labels and the policy admits this release's backup and verify jobs. - **Real-PostgreSQL tests and API contract gates.** Integration, e2e and contract tests run on PostgreSQL 16 in CI (a `postgres` service container pinned by digest, the same major and variant as the chart's database), and on SQLite locally unless `TEST_DATABASE_URL` is a PostgreSQL URL; the schema is made by the migrations and each test empties the tables afterwards. A migration round-trip test (upgrade, downgrade to base, upgrade) runs on both. The blocking `lint` job runs squawk on the migration SQL rendered offline for PostgreSQL (`scripts/ci/squawk.sh`, `.squawk.toml`). Schemathesis contract tests (`make test-contract`, marker `contract`, outside `make test`) run in the integration job with a fixed seed. The blocking `api-compat` job (`scripts/ci/oasdiff.sh`) fails a pull request that breaks the OpenAPI snapshot, unless it carries the `breaking-change` label; `labeled` and `unlabeled` are now pull request event types and every job runs on them. `api/deprecation.py` sets `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) headers. See [API lifecycle](./api-lifecycle.md) and [Testing](./testing.md#postgresql-contract-tests-and-the-two-gates). The contract tests found three defects, fixed without changing the published contract: `GET /items?page=` beyond a 64-bit offset and a NUL character in item text were 500s on PostgreSQL (now an empty page and a 422), and `/metrics` documented JSON for a text response. New dev dependency: `schemathesis`.
- **Database hardening.** `database.tls.caSecret` mounts a database CA from an existing Secret (read-only, backend and migration Job) and sets `DB_SSLROOTCERT`; `backend.extraInitContainers` renders init containers, such as a Cloud SQL Auth Proxy native sidecar, before `wait-for-db`. A `DATABASE_URL` carrying `ssl` or `sslmode` is refused, and in production a URL naming no host no longer counts as loopback. The migration Job keeps its logs after an automatic rollback (`helm.sh/resource-policy: keep`), and the runner retries only connection failures, never authentication or TLS errors. `DB_CONNECT_TIMEOUT_SECONDS` (10), `DB_STATEMENT_TIMEOUT_MS` (30000) and `DB_IDLE_IN_TRANSACTION_TIMEOUT_MS` (60000) apply to the app's PostgreSQL connections; `DB_MIGRATION_LOCK_TIMEOUT_MS` (10000) gives the migration run a `lock_timeout` and no statement timeout. `DB_SSLMODE` (`disable`, `require`, `verify-ca`, `verify-full`) and `DB_SSLROOTCERT` set TLS to the database; production refuses `disable` and `require` unless the database host is loopback (a Cloud SQL Auth Proxy sidecar), and the production chart values set `verify-full`. Timestamps are timezone-aware UTC on every database (no schema change). See [Database operations](./database.md#database-operations).
- **Schema-aware readiness.** `GET /api/v1/health` answers 200 when the database is reachable and at this release's head or at a revision this release does not know (a newer release migrated first), and 503 with `reason` `database_unreachable`, `schema_missing` or `schema_behind` otherwise. `/api/v1/healthz` stays process-only.
- **Production authentication.** `AUTH_MODE=oidc` verifies an `Authorization: Bearer` JWT (RS256/ES256 by default; an allowlist of RS*, PS*, ES*) against the provider's JWKS, and `AUTH_MODE=cloudflare-access` verifies the `Cf-Access-Jwt-Assertion` header against the team's `/cdn-cgi/access/certs` keys and the application's AUD tag (the cookie is ignored). Checked: algorithm allowlist and key type (so `none` and HS/RS confusion fail), required `kid`, no `crit`, exact issuer, audience, required `exp`, `nbf`/`iat` with `OIDC_CLOCK_SKEW_SECONDS`, tokens up to 8 KiB. The JWKS is cached (`JWKS_CACHE_TTL_SECONDS`), fetched once for concurrent cold requests, refetched for an unknown `kid` at most once per `JWKS_MIN_REFETCH_SECONDS`, and served stale for up to `JWKS_MAX_STALE_SECONDS` when the provider is down, then `503`. Failures are `401` problems with `WWW-Authenticate` (`error="invalid_token"`) and a generic detail. New variables `OIDC_*`, `CF_ACCESS_*` and `JWKS_*`; new dependency `pyjwt[crypto]` (adds `cryptography`). Production accepts both modes without `ALLOW_ANONYMOUS`; `gateway` and `bearer` stay as reference modes. See `wiki/security.md#authentication--authorization`.
- **Request safety.** `X-Request-Id` is kept only when it is at most 64 characters of `[A-Za-z0-9._-]` (otherwise a new id is generated, and the rejected value is never logged) and is echoed on every response. A valid W3C `traceparent` puts its trace id on every log line (`trace_id`, JSON and text) and on error bodies; `outgoing_trace_headers()` forwards it. `MAX_REQUEST_BODY_BYTES` (default 10 MiB, equal to the chart's ingress `proxy-body-size`) answers `413`, and `ALLOWED_HOSTS` (default `*`; production refuses `*` or an empty list) answers `400` for any other `Host`, with the health and metrics paths exempt. The chart renders `ALLOWED_HOSTS` from the ingress hosts, the backend Service names and `backend.extraAllowedHosts` (`values.local.yaml` adds `localhost,127.0.0.1`); `smoke-test.sh` has a `--host` option, which the deploy and e2e scripts use with the backend Service name. The rate limiter and the host check skip exact probe and metrics paths. See `wiki/security.md#request-limits-and-trusted-hosts`.
- **Trusted client IP.** `TRUSTED_PROXY_CIDRS` (default empty) and `TRUST_CF_CONNECTING_IP` (default `false`) drive one resolver, `ClientIpMiddleware`, the outermost middleware: `CF-Connecting-IP` is believed only from a peer in those ranges and only when its flag is on, `X-Forwarded-For` only from such a peer (read from the right, skipping trusted hops), and every other peer is the client. The rate limiter and the request log (now `... client=<ip>`) use it, so clients behind the gateway no longer share one bucket (previously every client behind a proxy outside Uvicorn's default `127.0.0.1` allow-list keyed on the proxy's address). Production refuses `TRUST_CF_CONNECTING_IP=true` with no ranges. `TRUSTED_PROXY_CIDRS` refuses entries with host bits set (`10.1.2.3/8`). See `wiki/security.md#client-ip` for what the proxies must do per edge mode. The chart sets both in `config:`, documents that with the WAF on the backend sees `X-Forwarded-Proto: http`, and sets Envoy's upstream idle timeout (`waf.upstreamIdleTimeoutSeconds`, 60 s; Envoy's default is one hour) below the backend keep-alive.
- **Typed settings.** One `pydantic-settings` class, `Settings` (`backend/settings.py`), declares every environment variable the backend reads (including `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `TEST_DATABASE_URL`, `SQLITE_PATH` and the `AUTH_*` family), with a type, the existing default and a description; `create_app()` builds it once and keeps it on `app.state.settings`, and a test fails if anything else in `src/` touches `os.environ`. Names and defaults are unchanged. An invalid configuration now stops startup with one error that names every invalid variable (and never prints a secret). `wiki/environment-variables.md` has a generated backend-settings section (`make env-docs`; `make env-docs-check` runs in `check-all-dry` and CI).
- **Production rules.** With `ENV=production` (or `prod`) the backend refuses to start on SQLite or no database, credentialed CORS with an empty or `*` origin list, a CORS origin that is not a bare `scheme://host[:port]`, `AUTH_MODE=none` without `ALLOW_ANONYMOUS=true`, any `TEST_DATABASE_URL`, and the Swagger UI or the OpenAPI JSON turned on without `ALLOW_PRODUCTION_DOCS=true`. `/docs` and `/openapi.json` are now off by default in production; new variables `OPENAPI_URL`, `ALLOW_ANONYMOUS` and `ALLOW_PRODUCTION_DOCS`. The chart's production values do not choose anonymous access: set `AUTH_MODE` (for example `gateway`) under `config:` before deploying, or the backend Pods never become ready and the release rolls back.
- **Weekly re-scan of the running and released images.** `rescan.yml` (Wednesday 05:41 UTC and manual) takes the newest successful deployment of each environment and the latest release, finds their digests through the run named in the deployment status (release assets, else the `image-digests` artifact of that run attempt; an expired artifact or a rollback is reported as not scannable), runs Grype by digest with the repository's ignore list and no VEX, and opens or updates one `vuln` issue per (vulnerability, package) for critical and high findings. Three jobs: `collect`, `scan` (the only one with `packages: read`) and `report` (`issues: write`). The release's draft now also carries `image-digests.env` and `scan.env`. New `wiki/vulnerability-management.md` sets the SLA (critical 7 days, high 30) and how a risk is accepted. `deploy-ops.yml` now records a deployment only for a rollback (`deployment: false` for the other operations).
- **Renovate, pin refresh and a blocking pin-drift check.** `renovate.json5` (inert until the app is installed) covers `tools/pins.tsv`, the annotated versions in `infra/security/config.yaml`, image digests, Dockerfiles and `uses:` pins, with a 7-day release age, one weekly group for minor and patch updates, and separate majors. `make pins-refresh` (`scripts/pins-refresh.sh`) writes the vendor-published checksum for every pin that differs and regenerates the hashed locks; `--check` is read-only. The new blocking `pins` job (behind `CI OK`, skippable on a pull request that touches no pin file) fails when a recorded checksum differs from the vendor's for that version, on changed rows for a pull request and on every row for `main` and the weekly `pins-drift.yml`. `.github/dependabot.yml` keeps Dependabot to security updates (`open-pull-requests-limit: 0`). The check anchors each pin to its vendor's url prefix, verifies every lock entry against PyPI (hashes and a 7-day age), retries transient fetch failures, and checks every row when the checker itself changes. `github-settings.sh` also turns on Dependabot alerts and security updates.
- **OpenSSF Scorecard.** `scorecard.yml` runs weekly and on push to `main`, publishes the result and uploads SARIF to code scanning (a private repository opts out with the variable `SCORECARD_ENABLED=false`; assurance, not a gate). The README shows the Scorecard badge. The hardening lint exempts the `analysis` job of `scorecard.yml` (and only it) from the environment rule for `id-token: write`, which publishing needs.
- **Pre-commit hooks and a blocking `hadolint` job.** `.pre-commit-config.yaml` has local hooks (ruff format, ruff, prettier, eslint, shellcheck, hadolint, gitleaks on staged changes, actionlint, yamllint for the chart values, and a placeholder-leftover check) that call the tool CI uses; `make precommit` runs them with the pinned pre-commit. The `hadolint` job lints every tracked Dockerfile and is behind `CI OK`. Dockerfile fixes: numeric `USER` (UID 10001, matching the chart), exec-form `HEALTHCHECK`, merged `RUN` layers, pinned pip.
- **Isolated build, keyless signing and attestations.** `reusable-build.yml` is now the only workflow that pushes, signs or attests images (`build`, `sbom`, `grype`, then `sign-attest`); `release.yml` calls it. After the blocking Grype gate each image digest is signed keyless with the pinned cosign, verified against the workflow identity, and given a SLSA provenance and a CycloneDX SBOM attestation (`push-to-registry`). On `v*` tags the SBOMs, the OpenVEX document and the licence report are uploaded to a draft GitHub Release (never published by the workflow). See `wiki/security.md` for how to verify an image.
- The signing step also verifies the workflow repository claim (a foreign repository can call a public reusable workflow and get the same identity), and the attestations run only for public repositories or when the variable `ATTESTATIONS_ENABLED` is `true`. Every `reusable-build.yml` job refuses to run outside a push to `main` or a `v*` tag.
- `ci_hardening_lint.py`: new check `image-push-isolation` (it also lints composite actions, `write-all`, buildx/bake/crane/oras pushes and pull_request callers), and `provenance` is now a real check (it no longer prints a SKIP). The JSON report has no `skipped` field any more.

### Removed
- **The chart's log-collector tier and all file logs.** The Fluentd DaemonSet, its RBAC and its namespace (`monitoring.logging`, `monitoring.fluentd`, `namespaces.loggingSuffix`) are gone: it ran as root, mounted a `hostPath` and could not run under the `restricted` Pod Security profile. Collecting node logs is now platform guidance ([Infrastructure, Collecting logs](./infrastructure.md#collecting-logs)). The `/app/logs` emptyDir, its mounts, `LOG_DIR` and the image's log directory are removed too: logs go to stdout only, and `/tmp` is the only emptyDir. Remove `monitoring.logging`, `monitoring.fluentd` and `namespaces.loggingSuffix` from your values files; the schema now rejects them.
- `infra/security/publish-sbom-registry.sh`, the `devsec.sh publish` subcommand and its tests; the SBOM is attested and published as a release asset instead.
- **The nginx static tier.** The template builds two images, backend and frontend. The Next.js server serves its own pages and `/_next/static` assets (hashed, immutable, one-year cache), `public/` files carry the cache table in `frontend/next.config.ts`, and `frontend/static-paths.ts` is the one list of static paths. `deploymentId` is set from the image version and commit, so a client caught mid-rollout reloads instead of breaking. A CDN in front caches the assets at the edge. Removed: `Dockerfile.nginx`, `infra/nginx/`, the nginx Deployment, Service, HPA and NetworkPolicy rules in the chart, the `NGINX_*` variables, the `--mode nginx` entrypoint mode and the nginx Compose service (Compose now runs backend, frontend and postgres). Ports: backend 8000, frontend 3000.
